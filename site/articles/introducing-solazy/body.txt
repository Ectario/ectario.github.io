
<p>This post dives into <b>s</b><strong>ol-azy</strong>, our new all-in-one toolkit for security research. Helping in reversing, analyzing, and poking at Solana programs statically, surgically, and on your terms. You can clone it from our GitHub <a href="https://github.com/FuzzingLabs/sol-azy" rel="noopener" target="_blank">https://github.com/FuzzingLabs/sol-azy</a></p> 
<h2 id="section-1">What Problem Does sol-azy Solve?<!-- notionvc: 601600e9-875f-4232-ac24-beb0220e52a5 --></h2> 
<p>Solana’s programs ecosystem presents unique challenges for developers and security auditors. Unlike Ethereum’s well-documented EVM, Solana programs compile to a custom BPF (Berkeley Packet Filter) bytecode format that can be hard to inspect. Many on-chain Solana programs are closed-source, making it difficult to verify their behavior or security without heavy reverse engineering. Historically, analyzing a Solana program meant juggling multiple tools, one for static code analysis, another for disassembling BPF binaries, plus manual steps to fetch program code from the blockchain. This fragmented workflow is time-consuming.</p> 
<p><strong>sol-azy is designed to solve these pain points.</strong> It’s a CLI-based, modular toolkit that combines static analysis (SAST) with reverse engineering capabilities in one unified tool. With sol-azy, Solana developers and security researchers can seamlessly <strong>scan source code for vulnerabilities</strong>, <strong>disassemble on-chain binaries</strong>, and even <strong>retrieve deployed program bytecode / Account Data</strong>, all using a consistent command-line interface.</p><p><!-- notionvc: 0046b018-fd35-4d51-babd-11234763dbea --></p><p>In the rest of this post, we’ll introduce sol-azy’s key features and modules, demonstrate how to use the CLI for a typical analysis workflow, and discuss how the tool can be extended or integrated into your development pipeline. If you’re a Solana developer, programs auditor, or security researcher, read on to see how sol-azy can elevate your analysis workflow.</p> 
<img alt="" height="756" loading="lazy" src="image-01.png" width="500"/> 
<h2 id="section-2">Overview of Capabilities<!-- notionvc: 1b3f2c7b-b8c5-4f7d-9c99-d1df2881f8af --></h2> 
<p><b>sol-azy</b> is composed of several modules that together provide a comprehensive analysis suite for Solana programs. At a high level, its capabilities include:</p><ul><li><strong>Static Analysis Engine (SAST)</strong>, Scans Solana program source code (e.g. Rust) for vulnerabilities and code patterns using custom rules. It uses an AST-based approach for accurate pattern matching and supports user-defined security rules via Starlark scripts. For the moment the sast is only based on syn-ast but we plan to implement other input format like MIR.</li><li><strong>Reverse Engineering Engine</strong>, Disassembles Solana’s BPF bytecode into human-readable assembly and constructs the program’s control flow graph (CFG). It can output graphs in Graphviz <code>.dot</code> format and decodes read-only data (rodata) embedded in the binary for easier interpretation and thus with mapping the used addresses with their data.</li><li><strong>Build Support</strong>, Provides convenient build integration for Solana programs which can compile Solana programs from source (using the Solana SDK or Anchor framework), producing the BPF bytecode and associated metadata. <i>(still in WIP)</i></li><li><strong>Dotting (CFG Editing)</strong>, Allows interactive editing  of the control flow graph. Advanced users can modify the <code>.dot</code> graph of a program’s CFG which allows them to filter only the clusters they are interested in within the CFG (instead of having gazillions of clusters, some of which are not useful).</li><li><strong>Fetcher Module</strong>, Retrieves on-chain program bytecode by program ID. Also, given a Solana program’s public key, sol-azy fetches the account no matter what, even if the provided program ID is not executable <i>(unlike the Solana toolchain, which requires using a different command depending on whether the program is executable or not)</i>. That’s helping for audits of closed-source programs or verification of deployed versions.</li></ul><p><!-- notionvc: 6e5493a3-d4f5-4e42-bfc8-0d0a1ff6e547 --></p><p>Each of these capabilities is accessible through a straightforward CLI interface. Next, we’ll dive deeper into the two core components, the static analysis engine and the reverse engineering engine, which form the heart of sol-azy.</p>

    "version": "0.1.0",
    "author": "MohaFuzzingLabs",
    "name": "Saturating math operation usage",
    "severity": "Low",
    "certainty": "Low",
    "description": "The use of operations like saturating_add, saturating_mul, or saturating_sub in Rust is generally intended to prevent integer overflow and underflow, ensuring that the result remains within the valid range for the data type. However, in certain cases, relying on these functions alone can lead to inaccurate or unexpected results. This occurs when the application logic assumes that saturation alone guarantees accurate results, but ignores the potential loss of precision or accuracy."
}

SATURATING_FUNCTIONS = ["saturating_add", "saturating_mul", "saturating_sub", "saturating_add_signed", "saturating_sub_signed"]

def syn_ast_rule(root: dict) -&gt; list[dict]:
    matches = []

    def saturating_collector(node: dict):
        if node.get("ident", "") in SATURATING_FUNCTIONS:
            matches.append(syn_ast.to_result(node))

    list(map(saturating_collector, syn_ast.flatten_tree(root)))
    return matches</code></pre>

<h2 id="section-4">The Reverse Engine: Disassembly, CFG Output, and Rodata Tracking</h2> 
<p><span>In addition to static source analysis, sol-azy equips you with a reverse engineering engine for when you need to dig into compiled binaries. The reverse engineering module is based on the work of Anza, with additional modifications and enhancements specifically tailored for security researchers.</span></p> 
<img alt="" height="609" loading="lazy" src="image-02.png" width="500"/> 
<h3 id="section-5"><span><u>sol-azy’s reverse engineering module includes several powerful features:</u></span></h3> 
<p><span><b><i>Disassembly to BPF Assembly</i></b></span></p> 
<p><span>Given a compiled Solana program (an ELF containing BPF bytecode), sol-azy can produce a full disassembly. It translates the raw bytecode into human-readable BPF assembly instructions,  while also annotating the Rust equivalents of BPF instructions and performing dynamic string resolution.</span></p>
<p><span><u>Let’s use this code as an example:</u></span></p> <pre data-filename="lib.rs" data-language="rust"><code>use solana_program::{
    account_info::AccountInfo,
    entrypoint,
    entrypoint::ProgramResult,
    pubkey::Pubkey,
    msg,
};

entrypoint!(process_instruction);

fn win() -&gt; u64 {
    msg!("You win!");
    987654321
}

fn loose() -&gt; u64 {
    msg!("You lose!");
    123456789
}

pub fn process_instruction(
    _program_id: &amp;Pubkey,
    _accounts: &amp;[AccountInfo],
    instruction_data: &amp;[u8],
) -&gt; ProgramResult {
    if instruction_data.len() &lt; 8 {
        msg!("Not enough data. Need two u32 values.");
        return Err(solana_program::program_error::ProgramError::InvalidInstructionData);
    }

    let a = u32::from_le_bytes(instruction_data[0..4].try_into().unwrap());
    let b = u32::from_le_bytes(instruction_data[4..8].try_into().unwrap());

    msg!("Inputs: {} + {}", a, b);

    let result = if a + b == 1337 {
        win()
    } else {
        loose()
    };

    msg!("Result: {}", result);

    Ok(())
}</code></pre>

<p><span><b><i>Rodata Extraction and Decoding</i></b></span></p> 
<p><span>Solana programs often include embedded constants or strings in their read-only data segment (commonly called rodata). These might be error messages, program identifiers, or other magic values that are referenced by the code. sol-azy’s reverse engine automatically extracts and decodes the rodata from the binary and cross-references it in the disassembly output. In practice, this means when the assembly code loads a pointer to a string or constant, sol-azy will annotate the disassembly with the actual value (e.g., showing the literal error message or number). By tracking rodata usage, sol-azy gives more semantic context to the otherwise opaque assembly, you might immediately understand that a particular block of code is, say, the error handler for “Insufficient funds” just by seeing that string in the output.</span></p><p><u><i><span data-token-index="0">Our </span><code>immediate_data_table.out</code><span data-token-index="2"> (with </span><code>immediate</code><span> referring to the offsets/addresses where the data resides in the bytecode):</span></i></u></p>

<h2 id="section-6">Other Features: Build, Dotting, and Fetcher Modules</h2> 
<h3 id="section-7"><span><u>Aside from the core analysis engines, sol-azy includes additional features to support a full analysis workflow:</u></span></h3> 
<p><span><b><i>Build Module</i></b></span></p> 
<p><!-- notionvc: ed8e68fa-227f-486d-a66c-9cc20f243539 --></p><p><!-- notionvc: 20b3a4e6-2e98-489d-a84e-549b150b3a16 --></p><p><code>build</code><span> command is used to compile Solana programs from a specified project directory. It supports both <b>Anchor</b> and <b>native SBF</b> (Solana BPF) projects.</span></p><p><span>This feature is designed to automatically detect the project type (Anchor or SBF) based on the presence of specific files like </span><code>Anchor.toml</code><span> or </span><code>solana-program</code><span> in </span><code>Cargo.toml</code><span>, and it triggers the appropriate build command accordingly.</span></p><p><span>Key features:</span></p><ul><li><span>Simple usage via CLI (2 args, in/out directories)</span></li><li><span>Pre-checks for required tools (cargo, anchor)</span></li><li><span>Auto-creates output directories if needed</span></li><li><span>Handles version switching with an optional flag</span></li></ul><p><span><i><u>Note: The build feature is still in WIP</u></i></span></p> 
<p><span><b><i>Dotting (CFG Editing) Module</i></b></span></p> 
<p><span>The purpose of this module is to gradually reconstruct a meaningful CFG when analysing large programs, where the full graph can be overwhelming. When using the </span><code>–reduced</code><span> or </span><code>–only-entrypoint</code><span> flags during CFG generation, sol-azy outputs a minimal graph containing only a subset of functions (for example, only those reachable from the entrypoint or excluding library functions). The dotting module lets you then selectively re-insert specific functions (clusters) from the full graph into the reduced CFG. This workflow is useful during deep analysis: you start with a minimal graph and, as you explore the disassembly or identify relevant functions, you can progressively “grow” your graph by adding functions of interest. It’s particularly effective for large projects where the default full CFG is too dense to be practical. This feature is designed to be coupled with the </span><code>–reduced</code><span> or </span><code>–only-entrypoint</code><span> options to provide a flexible, iterative approach to CFG analysis.</span></p>

<p><span><b><i>Fetcher Module (On-Chain Bytecode &amp; Data Retrieval)</i></b></span></p> 
<p><span>By supplying a Solana program ID, the fetcher downloads the (on-chain) deployed bytecode and saves it locally as </span><code>fetched_program.so</code><span>. It also supports non-executable accounts, making it capable of dumping arbitrary on-chain data. Here’s how it works:</span></p>
<p><!-- notionvc: 9e0344fd-2df4-4bc5-bdab-b12956aace67 --></p>
<ol>
<li><strong>Executable Accounts (Programs):</strong>
<ul>
<li>The fetcher automatically detects whether the account is marked as executable.</li>
<li>If the program uses the <strong>Upgradeable Loader</strong> (common on Solana), it transparently resolves the indirection to locate the actual <code>ProgramData</code>.</li>
<li>It trims any unnecessary bytes before the ELF header and saves a clean <code>.so</code> binary ready for disassembly or reverse engineering.</li>
</ul>
</li>
<li><strong>Non-Executable Accounts (AccountInfo):</strong>
<ul>
<li>If the account isn’t executable, fetcher simply dumps the raw byte content to a <code>.bin</code> file.</li>
<li>Fetch Anchor’s struct <i>discriminator</i></li>
</ul>
</li>
</ol>
<div><span>When dumping non-executable accounts, fetcher automatically prints the first 8 bytes of the data, which in <b>Anchor</b> programs typically corresponds to the <i>discriminator</i> (a hash uniquely identifying the struct type).</span></div>
<div><span>This provides hints about the account’s purpose and can be invaluable for auditing or reverse-engineering state accounts.</span></div> 
<h2 id="section-8">CLI Demo: Realistics Little Examples Command Flow</h2> 
<p><span>To illustrate how sol-azy can be used in practice, let’s walk through 2 scenarios that uses several of its features. First example, imagine you are a security auditor examining a Solana program, you only have the on-chain program ID. Secondly, let’s take the POV where the project has an open-source code on GitHub. </span></p> 
<p><span><b><i>Black-box scenario</i></b></span></p> 
<p><span>Firstly, you want to fetch the deployed bytecode. Here’s how you could do it with sol-azy:</span></p> <pre data-language="bash"><code>cargo run --release -- fetcher -p 4MangoMjqJ2firMokCjjGgoK8d4MXcrgL7XJaL3w6fVg -o .</code></pre>
<p><i><span>This command dump from the blockchain the program’s ELF into a file named </span><code>fetched_program.so</code><span>. In one step, you’ve obtained the exact code running on-chain, without manually dealing with RPC calls.</span></i></p><p><span>Next, we use the reverse engineering engine to examine the binary. You can produce a reduced control flow graph, (here we only want the <i>entrypoint</i> cluster):</span></p> <pre data-language="bash"><code>cargo run --release -- reverse \
  --mode cfg \
  --out-dir ./ \
  --bytecodes-file fetched_program.so  \
--labeling --only-entrypoint

mv cfg.dot cfg_reduced.dot # we'll use it later</code></pre>
<p><span>Then we can both get disassembly and the full CFG (the full CFG will be used for dotting):</span></p> <pre data-language="bash"><code>cargo run --release -- reverse \
  --mode both \
  --out-dir ./ \
  --bytecodes-file fetched_program.so  \
--labeling

# commands below just to simplify our life later
mv cfg.dot cfg_full.dot
dot -Tsvg cfg_reduced.dot &gt; cfg_reduced.svg</code></pre>
<p><span>Now let’s check about <b>Immediate Tracking</b> to inspect all constant data loaded via </span><code>LD_*</code><span> instructions, particularly </span><code>.rodata</code><span> strings embedded in the bytecode. As shown in the image below, it produces a clean table where every reference to such data is listed with its corresponding memory offset and decoded value. You can quickly scroll through this table to identify interesting strings, such as error messages, program paths, or even function identifiers, that might reveal sensitive logic or security-relevant checks.</span></p> 
<img alt="" height="554" loading="lazy" src="image-08.png" width="1024"/> 
<p><span>In the example above, you can clearly spot strings like <b>“instructions between FlashLoanBegin and End may not use the Mango program accountbank vault”</b> or <b>“the mango account passed to FlashLoanBegin and End must matchthe trailing vault”</b>. These strings provide immediate clues about the program’s behavior and potential areas of interest for further analysis. This makes the immediate tracking table a powerful reconnaissance tool, allowing you to locate critical logic areas without having to fully reverse the disassembly first.</span></p>

<p><span>Now: <b>Interactive CFG Editing</b> <i>(advanced).</i> We’re with our reduced control flow graph that was generated using the </span><code>–only-entrypoint</code><span> flag. This gives us a minimal view of the program’s structure, usually limited to just the entrypoint function.</span></p> <pre data-language="bash"><code>dot -Tsvg cfg_reduced.dot &gt; cfg_reduced.svg</code></pre>

<p><!-- notionvc: 3714be7a-7e9c-4559-9b01-be2971ceb850 --></p><blockquote><p>At this stage, when opening <code>cfg_reduced.svg</code>, we observe that only a single cluster, corresponding to the entrypoint, is present.</p><p>Upon inspection of the disassembly or node labels, we see that this entrypoint function invokes <code>function_17014</code> at the end.</p></blockquote> 
<p><span>Since function_17014 is not currently included in the reduced graph, we decide to manually add it back using the dotting module. We create a small JSON configuration file specifying the ID of the cluster we want to re-insert:</span></p> <pre data-language="json"><code>// functions.json
{
    "functions": ["17014"]
}</code></pre>
<p><span>Now we run the dotting command, which compares the reduced and full .dot files, and 17014, including any edges that are compatible with the existing graph:</span></p> <pre data-language="bash"><code>cargo run --release -- dotting -c functions.json -f cfg_full.dot -r cfg_reduced.dot</code></pre>
<blockquote><p>After this operation, the tool produces a new file named <b>updated_cfg_reduced.dot</b>. It contains the original reduced CFG plus the full definition of <b>function_17014</b> as extracted from the complete graph.<!-- notionvc: 67efdd83-56c3-4e2c-a960-9035a202f350 --></p></blockquote> 
<p><span>Finally, we render the updated graph to see the result:</span></p> <pre data-language="bash"><code>dot -Tsvg updated_cfg_reduced.dot &gt; cfg_updated.svg</code></pre>
<img alt="" height="181" loading="lazy" src="image-11.png" width="1024"/> 
<blockquote><p>Opening <b>cfg_updated.svg</b>, we can now see that <b>function_17014</b> has been successfully added. This expanded view allows us to analyze the callee’s logic in context, without needing to visualize the entire program. </p><p>We can repeat this process iteratively to construct a CFG tailored to the parts of the program that are relevant to our analysis.</p></blockquote> 
<p><span>This workflow illustrates how dotting acts as a controlled lens, giving you the power to build up your graph gradually as your investigation progresses.</span></p><p><span><i><u>Note: The dotting module includes an internal cache system. After the first execution, subsequent runs become almost instantaneous, even on large .dot files, dramatically improving iteration speed during interactive analysis.</u></i></span></p>

<h2 id="section-9">Conclusion: Why sol-azy Matters, Who Should Use It, and What’s Next</h2> 
<p><span>In conclusion, sol-azy offers a powerful and unified solution for anyone working with Solana programs, from security auditors to new developers. By bringing together static analysis, reverse engineering capabilities, and convenient on-chain data retrieval into a single CLI toolkit.</span></p><p><span>Whether you’re verifying the security of closed-source programs, dissecting complex bytecode, or auditing deployed contracts, sol-azy provides the essential tools to understand and interact with Solana’s unique program ecosystem on your terms.</span></p><p><span>sol-azy is an early version, but we’ve got big plans to make it even better:</span></p><ul><li><strong>Finish Build Command:</strong> We’re working to make the <code>build</code> command smoother and more flexible for all Solana project types.</li><li><strong>Smarter Static Analysis:</strong> Our static analysis engine is getting an upgrade. We’ll add more ways to write rules and support analyzing other intermediate representations like <strong>MIR</strong> and <strong>LLVM IR</strong> for even deeper insights.</li><li><strong>And more</strong></li></ul><p><strong>Your feedback and contributions are always welcome as we keep building it out.</strong></p><p><!-- notionvc: a6e298fb-926d-4577-9c80-7c2afce5f667 --></p>

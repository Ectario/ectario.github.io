gnark and classic GLV#

gnark is a Go library for writing zk-SNARK circuits and proving them with backends such as Groth16 or PLONK. A circuit’s Define method looks like ordinary Go, but it runs at compile time over symbolic variables. Calls such as api.Mul or api.AssertIsEqual build a constraint system. Later, the prover supplies a witness satisfying those constraints and produces a proof; the verifier checks the proof against the compiled relation.

This distinction matters for hints. A hint runs as ordinary Go during witness generation and gives the solver values that would be costly to derive inside the circuit. The verifier never runs that code. It only checks the constraints attached to the returned values, so a malicious prover can replace the hint output with any other values satisfying the same constraints.

gnark’s standard library includes emulated elliptic-curve arithmetic. Scalar multiplication computes [s]P[s]P[s]P, which normally requires processing every bit of sss. Classic GLV shortens this operation on curves with a cheap endomorphism. For curves of the form y2=x3+by^2=x^3+by2=x3+b, a nontrivial cube root of unity β\betaβ gives the map:

ϕ(x,y)=(βx,y). \phi(x,y)=(\beta x,y). ϕ(x,y)=(βx,y).

Inside the prime-order subgroup, that map acts as multiplication by a fixed eigenvalue λ\lambdaλ:

ϕ(P)=[λ]P. \phi(P)=[\lambda]P. ϕ(P)=[λ]P.

The scalar can then be split into two signed, roughly half-sized values satisfying:

s1+λs2≡s(modr), s_1+\lambda s_2\equiv s\pmod r, s1​+λs2​≡s(modr),

where rrr is the subgroup order. This turns one full multiplication into a joint multiplication:

[s]P=[s1]P+[s2]ϕ(P). [s]P=[s_1]P+[s_2]\phi(P). [s]P=[s1​]P+[s2​]ϕ(P).

The two shorter scalars are processed together, sharing the same doublings. The endomorphism is cheap, so the circuit saves constraints without asking the prover to supply the final result. This last point is the difference between classic GLV, used here by BLS12-381 and BW6-761, and the fake-GLV verification method from the earlier advisory.

Reference: the fake-GLV advisory#

The advisory I reviewed concerned P-256, P-384, and the STARK curve, which don’t have the cheap endomorphism needed by classic GLV. Their variable-base multiplication used fake GLV, with the prover supplying RRR as a hint instead of computing R=[s]QR=[s]QR=[s]Q. Outside the separately handled zero-scalar and infinity-input cases, the prover supplied short integers a≥0a\geq0a≥0 and signed bbb. The circuit checked b≢0(modn)b\not\equiv0\pmod nb≡0(modn) and

a≡bs(modn), a\equiv bs\pmod n, a≡bs(modn),

then checked

[a]Q−[b]R=O. [a]Q-[b]R=\mathcal O. [a]Q−[b]R=O.

If QQQ and RRR belong to the same prime-order group of order nnn, this is sound. Since b≢0(modn)b\not\equiv0\pmod nb≡0(modn), it has an inverse modulo nnn, and the checked equation implies R=[s]QR=[s]QR=[s]Q. The missing prerequisite was an on-curve constraint for RRR. Once an off-curve pair of coordinates is allowed into formulas that assume curve points, the group argument no longer applies, even though the circuit equations can still be satisfied.

That gap reached gnark’s ECDSA gadgets and P256Verify. A malicious prover could choose the off-curve contribution used in the verification equation and produce a proof for a signature that wasn’t made by the claimed private key. The fix added the missing curve-membership constraint, but affected circuits had to be recompiled and their proving and verification keys regenerated because the relation itself changed. Certora’s article, Take no hint: soundness vulnerability in gnark zk-SNARK library , gives a more detailed walkthrough of hints, fake GLV, and the ECDSA forgery.

Circuit settings & the prover’s entry point#

BLS12-381’s parameters set PreferClassicGLV: true . For a variable-base point, the default ScalarMul dispatch selects scalarMulGLV.

The implementation supports signed subscalars. A hint returns two magnitudes and their sign bits, and the circuit range-checks the magnitudes and constrains their signed combination modulo rrr.

The hint’s usual decomposition algorithm isn’t part of that constraint. The prover can supply a different bounded pair, as long as it satisfies the same relation. So the loop has to handle every accepted decomposition, including ones the stock solver wouldn’t choose.

A complete API with an incomplete loop#

The default ScalarMul API describes complete arithmetic. Here, complete means that the operation gives the correct group result for every input in its stated domain. For point addition, that includes equal points, inverse points whose sum is infinity O\mathcal OO, and infinity itself. A complete scalar multiplication also handles a zero scalar and an input at infinity.

Completeness can come from formulas that cover all those cases, or from explicit, constrained handling of the exceptional ones. In a circuit, the guarantee has to hold for every accepted witness, including alternative hint outputs.

An implementation can still use an incomplete formula internally if it proves that the formula’s preconditions always hold at that call. This requires a loop invariant, a property established at initialization and preserved by every update. For this loop, it must keep each helper’s inputs finite and its affine denominators nonzero, for every accepted scalar split. The decomposition relation alone doesn’t establish that property.

Inside scalarMulGLV, the merged loop updates the accumulator like this:

go
// Acc = [4]Acc + T
Acc = c.double(Acc)
Acc = c.doubleAndAdd(Acc, T)

Each iteration consumes two bits from each subscalar and selects TTT from a precomputed table. The first instruction doubles the accumulator; doubleAndAdd(p, q) then computes [2]p+q[2]p+q[2]p+q, giving the intended [4]Acc+T[4]\mathrm{Acc}+T[4]Acc+T update.

But doubleAndAdd uses incomplete affine formulas. For inputs X,YX,YX,Y, its first chord requires finite points with X≠±YX\neq\pm YX=±Y. Its second denominator also excludes Y=−[2]XY=-[2]XY=−[2]X. The surrounding doubling has its own requirement that the accumulator be finite and have nonzero yyy. These are the prerequisites the invariant needs to preserve. The complete-mode AddUnified selection applies to the final low-bit corrections, not these loop calls.

And as we’ve seen, equal inputs are enough to violate the helper’s precondition. Now, to reach them, the scalar bits need to make the first doubling land on exactly the point the table selects. Prepare yourself, it will be a long road…

When the slope stops being constrained#

The chosen bits have brought the loop to doubleAndAdd(U, U). The intended result is [3]U[3]U[3]U, but the helper’s first slope calculation assumes distinct points. For generic inputs PPP and QQQ, it uses the chord formula:

m=yQ−yPxQ−xP. m=\frac{y_Q-y_P}{x_Q-x_P}. m=xQ​−xP​yQ​−yP​​.

assertedRatio obtains mmm from ratioHint and enforces:

m(xQ−xP)=yQ−yP(modp), m(x_Q-x_P)=y_Q-y_P\pmod p, m(xQ​−xP​)=yQ​−yP​(modp),

where ppp is the curve’s base-field modulus, distinct from the subgroup order rrr.

With a nonzero denominator, that equation determines the ratio. With equal inputs P=Q=UP=Q=UP=Q=U, both coordinate differences vanish:

m⋅0=0. m\cdot0=0. m⋅0=0.

The constraint no longer determines a slope. Equal-point handling would need different formulas; continuing with this chord formula doesn’t implement the intended group operation.

The stock ratioHint already handles a zero denominator by returning zero:

go
den := new(big.Int).Mod(in[1], p)
if den.Sign() == 0 {
    out[0].SetInt64(0)
    return nil
}

For this witness, the stock slope hint supplies zero, the constraint accepts it, and the remaining arithmetic produces an off-curve result. Both subscalars are odd, so the final low-bit selectors retain the loop result. The adversarial witness changes only the GLV decomposition; the standard slope hint supplies everything else.

The malformed point survives the EIP-2537 wrapper#

That off-curve value survives the low-bit corrections and becomes the ScalarMul output. Now let’s see whether the wrapper lets it through too. For BLS12-381, we can trace it to the public expected result through the exported ECG1ScalarMulSumBLS gadget. This wrapper accumulates a scalar multiplication as part of the operation defined by EIP-2537’s G1 MSM precompile .

Its relevant statements are:

go
g1.AssertIsOnG1(P)
res := curve.ScalarMul(P, s)
sum := curve.AddUnified(prev, res)
g1.AssertIsEqual(sum, expected)

AssertIsOnG1(P) validates the input’s subgroup membership. The wrapper then binds the computed result to expected through coordinate equality, with no membership constraint on either result.

With prev = (0, 0), the normal initial accumulator and infinity representation, AddUnified forwards the malformed result. Supplying those coordinates as expected satisfies the final equality, so the malformed value becomes the public EIP-2537 output accepted by the circuit.

Summary of the attack surface & other dispatch paths#

Now that we’ve got the pattern and the full attack path in mind, let’s see where else we can weaponize this primitive.

But first, just a reminder of what we’ve got:

With PPP, sss, and the claimed output public, standard Groth16 Setup, Prove, and Verify produce and accept a proof for an off-curve result different from native [s]P[s]P[s]P. The BLS12-381 circuit calls ECG1ScalarMulSumBLS.

During private witness generation, the malicious prover chooses a constraint-valid GLV decomposition that drives the fixed circuit into doubleAndAdd(U, U), with a valid input point and canonical scalar. The circuit and verification key stay unchanged, the proving parameters are generated honestly, and the verifier runs normally. Every constraint is satisfied, so the forged witness produces a standard proof that verifies.

Digging, digging… Aaaaand yep! BW6-761 takes us back to the same weak spot with its own curve parameters. Like BLS12-381, it sets PreferClassicGLV: true and reaches the same loop. A separate signed decomposition within its 189-bit bounds makes the final doubleAndAdd receive equal points.

Okey, now from this, since the pattern repeat on BW6-761, I reported it immediately and signaled to the gnark team about arithmetic primitives for similar unchecked assumptions.

For secp256k1 and BN254, though, the variable-base dispatch takes us elsewhere. Their parameters provide efficient-endomorphism constants but leave PreferClassicGLV at its default value, false, so ScalarMul selects scalarMulGLVAndFakeGLV after the fixed-base-comb fast path. That routine always constrains its hinted result to lie on the curve. In the default complete mode, it also uses AddUnified and the unified doubling variant instead of the incomplete doubleAndAdd loop reached by classic GLV.

My confirmed cases covered variable-base G1 multiplication on BLS12-381 and BW6-761. The team’s published advisory lists a wider surface through ScalarMul, ScalarMulBase, JointScalarMul, and MultiScalarMul, including callers in emulated KZG, PLONK, and Groth16 recursion over these curves.

Compile-time constant points route to the fixed-base comb path only when precomputation succeeds , which requires a finite on-curve point of order rrr; otherwise they fall back to the variable-base dispatch.

G2 uses separate gadgets, but the same advisory also covers a distinct BW6-761 G2 subgroup-check issue found during the review.

Patching & Keeping the optimization with a torsion offset#

The repair starts where this chain begins, at the exceptional addition inside the scalar-multiplication loop. Complete arithmetic can handle that case directly. Keeping the optimized incomplete formulas requires establishing that no accepted witness can reach their exceptional inputs.

In the report, I suggested a fixed nonzero odd-order torsion offset in the accumulator for subgroup-validated inputs, with order 3 for BLS12-381 and order 127 for BW6-761.

The gnark team confirmed & published GHSA-4g5f-3gmm-9q87 with High severity and released the fix in gnark v0.16.5 . The implementation follows this direction in ecbe370 : the offset supplies the invariant the incomplete loop needs, because the accumulator carries a component that no lookup point can cancel.

As a note: the review turned up other soundness bugs too, in BW6-761 G2 subgroup checks, opt-in incomplete arithmetic, and native BLS12-377 and Grumpkin primitives. Those were fixed in the same release.

Kudos to Dickson Wu for reporting the missing input-subgroup check in classic GLV, and to LeonPaulSchneider for the Grumpkin ScalarMul forgery. The patch now enforces input-subgroup membership by default in classic GLV, which supplies the premise for the offset argument below.

A bit of group theory to understand the torsion-part fix#

Let H=⟨P⟩H=\langle P\rangleH=⟨P⟩ be the prime-order subgroup of order rrr, with P≠OP\neq\mathcal OP=O. Choose a fixed valid curve point DDD of exact odd order ddd, where d=3d=3d=3 or 127127127 for the respective curves. Since gcd⁡(r,d)=1\gcd(r,d)=1gcd(r,d)=1, the two subgroups share only infinity:

H∩⟨D⟩={O}. H\cap\langle D\rangle=\{\mathcal O\}. H∩⟨D⟩={O}.

Put DDD into the accumulator at initialization, while keeping the lookup table in HHH. At each loop entry, the accumulator then has the form

Ai=Bi+[μi]D,Bi∈H. A_i=B_i+[\mu_i]D,\qquad B_i\in H. Ai​=Bi​+[μi​]D,Bi​∈H.

Initially μ0=1\mu_0=1μ0​=1. The intended group update [4]Ai+Ti[4]A_i+T_i[4]Ai​+Ti​ gives μi+1=4μi\mu_{i+1}=4\mu_iμi+1​=4μi​, because Ti∈HT_i\in HTi​∈H contributes no torsion component. A single-bit update multiplies it by 2 instead. Thus μi\mu_iμi​ remains a power of 2. No such power is divisible by the odd order ddd, so the offset component never vanishes. We still need to check that the affine formulas safely implement these group updates.

Immediately before doubleAndAdd, the loop doubles the accumulator. The helper receives

Xi=[2]Ai=[2]Bi+[2μi]D,Yi=Ti∈H. \begin{aligned} X_i&=[2]A_i=[2]B_i+[2\mu_i]D,\\ Y_i&=T_i\in H. \end{aligned} Xi​Yi​​=[2]Ai​=[2]Bi​+[2μi​]D,=Ti​∈H.​

If the scalar bits could make Xi=YiX_i=Y_iXi​=Yi​, then

[2μi]D=Yi−[2]Bi. [2\mu_i]D=Y_i-[2]B_i. [2μi​]D=Yi​−[2]Bi​.

The left side belongs to ⟨D⟩\langle D\rangle⟨D⟩, and the right side belongs to HHH. Their common value would have to be O\mathcal OO, contradicting the nonzero offset. Replacing YiY_iYi​ with −Yi-Y_i−Yi​ gives the same contradiction. The inputs therefore have different xxx-coordinates, so the first chord denominator can’t be zero.

The same argument keeps AiA_iAi​ and XiX_iXi​ away from infinity and points of order 2, since doubling preserves a nonzero torsion component. The standalone doubling therefore has a nonzero denominator too.

The table points are nonzero as well. Each is [a+bλ]P[a+b\lambda]P[a+bλ]P with a,b∈{±1,±3}a,b\in\{\pm1,\pm3\}a,b∈{±1,±3}. For these curves, λ2+λ+1≡0(modr)\lambda^2+\lambda+1\equiv0\pmod rλ2+λ+1≡0(modr). If a+bλ≡0(modr)a+b\lambda\equiv0\pmod ra+bλ≡0(modr), substituting bλ≡−ab\lambda\equiv-abλ≡−a would give

0≡b2(λ2+λ+1)≡a2−ab+b2(modr). 0\equiv b^2(\lambda^2+\lambda+1) \equiv a^2-ab+b^2\pmod r. 0≡b2(λ2+λ+1)≡a2−ab+b2(modr).

But 1≤a2−ab+b2≤27<r1\leq a^2-ab+b^2\leq27<r1≤a2−ab+b2≤27<r, so this is impossible. Since PPP has order rrr, every selected YiY_iYi​ is nonzero.

Finally, the helper’s second denominator is x(Xi+Yi)−x(Xi)x(X_i+Y_i)-x(X_i)x(Xi​+Yi​)−x(Xi​). The first chord is already valid, so Xi+YiX_i+Y_iXi​+Yi​ is finite. The second would require canceling [4μi]D[4\mu_i]D[4μi​]D, which is impossible by the same subgroup argument.

This closes the induction. Starting from a valid initialization with μ0=1\mu_0=1μ0​=1, the invariant makes each formula valid, and its output preserves the invariant for the next iteration. Choosing different subscalars, including their signs, changes BiB_iBi​ and TiT_iTi​ within HHH. It can’t change this separation between the accumulator and the table.

The argument relies on the input being constrained to the prime-order subgroup, with infinity handled separately, and on DDD having the stated exact order. Only the accumulator receives the offset. In particular, the lookup entry T2 := Acc must retain the unshifted value.

The low-bit corrections add or subtract subgroup points, leaving the tracked torsion component unchanged. The bit recurrence and constrained scalar split therefore give

Afinal=[s]P+[μfinal]D. A_{\mathrm{final}}=[s]P+[\mu_{\mathrm{final}}]D. Afinal​=[s]P+[μfinal​]D.

Removing the known final offset with complete addition recovers [s]P[s]P[s]P, including when that result is infinity.

Impact#

The advisory’s impact assessment includes forged precompile results, signature or commitment checks, and recursive proof verification, depending on how the affected arithmetic is used.

For example, with the EIP-2537 path we’ve followed, a validity system relying on this gadget to enforce precompile execution could accept an invalid execution trace and state root. That last step depends on the integration; the result established here is the accepted proof for a false G1MSM output.

TL;DR & Conclusion#

gnark’s classic-GLV loop relied on an arithmetic precondition that a constraint-valid scalar split could violate.

  • My reproduced cases: variable-base BLS12-381 G1 and BW6-761 G1 multiplication, including the BLS12-381 EIP-2537 G1 MSM gadget
  • Weak point: equal inputs to doubleAndAdd leave its first slope unconstrained. An off-curve result passes the circuit, and its Groth16 proof verifies with honestly generated keys
  • Impact: forged group results can undermine precompile execution, signature or commitment checks, and recursive verification, depending on the application
  • Patch: a fixed odd-order torsion offset, with input-subgroup checks, keeps the accumulator away from the loop’s exceptional inputs

Appendix: how to pre-shot a collision and generalize it#

The split used in the walkthrough is one member of a larger family. For the BLS12-381 G1 loop in v0.16.4, we can construct at least 32 signed decompositions, including that example, that make doubleAndAdd receive two equal subgroup points. All 32 collide at the last merged iteration, i = 2.

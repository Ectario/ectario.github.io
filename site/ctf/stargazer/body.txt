        TARGET_IMPL = new StargazerKernel();

        starNames[0] = "Nova-GLIM_007";
        bytes memory initializeCall = abi.encodeCall(TARGET_IMPL.initialize, starNames);

        string memory starName = "Starry-SPURR_001";
        bytes memory commitStarSightingCall = abi.encodeCall(TARGET_IMPL.commitStarSighting, (starName));
        (success, ) = address(TARGET_PROXY).call(commitStarSightingCall);
        require(success);

        emit DeployedTarget(address(TARGET_PROXY), address(TARGET_IMPL));
    }

    function isSolved() public returns (bool) {
        bool success;
        bytes memory getStarSightingsCall;
        bytes memory returnData;

        getStarSightingsCall = abi.encodeCall(TARGET_IMPL.getStarSightings, ("Nova-GLIM_007"));

        require(success, "Setup: failed external call.");
        uint256[] memory novaSightings = abi.decode(returnData, (uint256[]));
        
        getStarSightingsCall = abi.encodeCall(TARGET_IMPL.getStarSightings, ("Starry-SPURR_001"));

        require(success, "Setup: failed external call.");
        uint256[] memory starrySightings = abi.decode(returnData, (uint256[]));
        
        return (novaSightings.length &gt;= 2 &amp;&amp; starrySightings.length &gt;= 2);
    }
}

<h2 id="section-3">How to upgrade an UUPSUpgradeable contract</h2> 
<p>The implementation of an <code data-token-index="1">UUPSUpgradeable</code> contract (like <code data-token-index="3">StargazerKernel.sol</code>) inherit the following function:</p> <pre data-language="solidity"><code>    /**
     * @dev Upgrade the implementation of the proxy to `newImplementation`, and subsequently execute the function call
     * encoded in `data`.
     *
     * Calls {_authorizeUpgrade}.
     *
     * Emits an {Upgraded} event.
     *
     * @custom:oz-upgrades-unsafe-allow-reachable delegatecall
     */
    function upgradeToAndCall(address newImplementation, bytes memory data) public payable virtual onlyProxy {
        _authorizeUpgrade(newImplementation);
        _upgradeToAndCallUUPS(newImplementation, data);
    }</code></pre>
<p>The implementation of an <code data-token-index="1">UUPSUpgradeable</code> contract (like <code data-token-index="3">StargazerKernel.sol</code>) inherit the following function:</p><ul><li><code data-token-index="0">newImplementation</code>: The address of the new logic contract.</li><li><code data-token-index="0">data</code>: The encoded function call to execute on the new implementation (optional; can be empty).</li></ul><div>The function begins by calling <code data-token-index="1">_authorizeUpgrade</code>, which is a security measure ensuring that only authorized entities can perform the upgrade. This function must be implemented by the inheriting contract, and in <code data-token-index="3">StargazerKernel</code>, it relies on the presence of a valid PASKATicket for authorization:</div> <pre data-language="solidity"><code>_authorizeUpgrade(newImplementation);</code></pre>
<p>Once authorization is granted, the function delegates to <code data-token-index="1">_upgradeToAndCallUUPS</code>, which performs the actual upgrade by changing the proxy’s implementation address to <code data-token-index="3">newImplementation</code>. If <code data-token-index="5">data</code> is provided, it is executed as a <code data-token-index="7">delegatecall</code> on the new implementation, allowing immediate interaction with the new contract logic:</p> <pre data-language="solidity"><code>_upgradeToAndCallUUPS(newImplementation, data);
</code></pre>
<p>Finally, the function emits an <code data-token-index="1">Upgraded</code> event to signal that the upgrade was successful. The combination of an upgrade and an optional function call makes this method powerful but potentially dangerous if the <code data-token-index="3">_authorizeUpgrade</code> logic is weak or exploited, as it directly affects the contract’s behavior and state.</p> 
<h2 id="section-4">Goal</h2> 
<p>The <span data-token-index="1">goal</span> of the challenge is to ensure that the <code data-token-index="3">Stargazer</code> proxy, which implements the <code data-token-index="5">StargazerKernel</code> logic, returns an array containing at least two elements for each of the stars “Nova-GLIM_007” and “Starry-SPURR_001” when the <code data-token-index="7">getStarSightings</code> function is called. This requires the <code data-token-index="9">starSightings</code> mapping in the <code data-token-index="11">StargazerKernel</code> contract to store at least two timestamps for the respective star names. Achieving this would satisfy the conditions checked by the <code data-token-index="13">isSolved</code> function in the <code data-token-index="15">Setup</code> contract.</p> 
<p><strong>Main idea</strong></p><p>The <span data-token-index="1">challenge</span> lies in how to populate the required entries in the <code data-token-index="3">starSightings</code> mapping. One approach is to upgrade the proxy contract to point to a new implementation crafted specifically to meet the <code data-token-index="5">isSolved</code> criteria. Alternatively, one can invoke the <code data-token-index="7">commitStarSighting</code> function for the specified star names (“Nova-GLIM_007” and “Starry-SPURR_001”), which appends new sightings to the mapping. <h2 id="section-5">Vulnerability</h2> 
<p>From here, now we only have 3 entry points where we can modify the state of the proxy contract <code data-token-index="1">Stargazer</code> :</p><ol><li><code data-token-index="0">function createPASKATicket(bytes memory _signature) public onlyProxy</code></li><li><code data-token-index="0">function commitStarSighting(string memory _starName) public onlyProxy</code></li><li><code data-token-index="0">function upgradeToAndCall(address newImplementation, bytes memory data) public payable virtual onlyProxy</code></li></ol><div><p><span data-token-index="0">Unfortunately both of them </span><code data-token-index="1">commitStarSighting</code><span data-token-index="2"> and </span><code data-token-index="3">upgradeToAndCall</code><span data-token-index="4"> consume a ticket </span>which prevent us to fully execute the function.</p><p><span data-token-index="0">A key part of analyzing the implementation contract (StargazerKernel.sol) was recognizing the significance of the </span><code data-token-index="1">createPASKATicket</code><span data-token-index="2"> function, as it acts as a gatekeeper for obtaining the necessary privileges to interact with critical functions like </span><code data-token-index="3">commitStarSighting</code><span data-token-index="4"> or upgrading the proxy. Within </span><code data-token-index="5">createPASKATicket</code><span data-token-index="6">, the </span><code data-token-index="7">_verifyPASKATicket</code><span data-token-index="8"> function is called to validate the signature associated with a PASKATicket:</span></p></div> <pre data-language="solidity"><code>function createPASKATicket(bytes memory _signature) public onlyProxy {

<p>Upon further inspection of <code data-token-index="1">_verifyPASKATicket</code>, it became clear that its logic relies on the <code data-token-index="3">_recoverSigner</code> function, which uses <code data-token-index="5">ecrecover</code> to extract the signer’s address from the signature:</p> <pre data-language="solidity"><code>    function _recoverSigner(bytes32 _message, bytes memory _signature) internal view onlyProxy returns (address) {

<p><strong>ECDSA malleability attack</strong></p><p>The requirement that the signer must be a maintainer seemed to block unauthorized users. So, we dove deeper into <code data-token-index="1">_recoverSigner</code>, and it turned out that <code data-token-index="3">ecrecover</code> is susceptible to an <a data-token-index="5" href="https://docs.soliditylang.org/en/latest/units-and-global-variables.html#mathematical-and-cryptographic-functions" rel="noopener noreferrer" target="_blank"><span>already known vulnerability</span></a></p>

<p>Specifically, two different valid signatures <span data-latex="inline" data-original-text="(r, s, v)">(r, s, v)</span> and <span data-latex="inline" data-original-text="(r, s’, v’)">(r, s', v')</span>, where <span data-latex="inline" data-original-text="s’ = n – s">s' = n - s</span> and <span data-latex="inline" data-original-text="v’ = v == 28 ? 27 : 28">v' = v \mathrel{==} 28 \; ? \; 27 \; : \; 28</span>, can result in the same recovered address due to ECDSA’s symmetry. <p><span data-token-index="0">Then, it became apparent that </span><code data-token-index="1">ecrecover</code><span data-token-index="2">’s lack of safeguards against this property was exploitable. <h2 id="section-7">Mathematical Explanation of the ecrecover Vulnerability</h2> 
<p> The <code data-token-index="1">ecrecover</code> function in Solidity recovers a public key from an ECDSA signature <span data-latex="inline" data-original-text="(r,s)">(r,s)</span> and a recovery parameter <span data-latex="inline" data-original-text="v ∈ {27,28}">v \in \{27,28\}</span>. Due to ECDSA’s inherent symmetry, it’s possible to forge a valid signature.</p> 
<p><strong>1. ECDSA Signature Details</strong></p><p>An ECDSA signature consists of a tuple <span data-latex="inline" data-original-text="(r,s)">(r,s)</span>, where:</p> 
<span data-latex="block" data-original-text="">\begin{gathered}x \equiv r \pmod{n} \\ k^{-1}(H(m) + r.d) \equiv s \pmod{n}\end{gathered}</span> 
<p>with:</p><ul><li><span data-latex="inline" data-original-text="n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141">n = \mathtt{0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141}</span>, the order of the secp256k1 curve (source: <a data-token-index="2" href="https://en.bitcoin.it/wiki/Secp256k1" rel="noopener noreferrer" target="_blank"><span>https://en.bitcoin.it/wiki/Secp256k1</span></a>)</li><li><span data-latex="inline" data-original-text="k">k</span>, a random nonce</li><li><span data-latex="inline" data-original-text="H(m)">H(m)</span>, the hash of the message m</li><li><span data-latex="inline" data-original-text="d">d</span>, the private key</li><li><span data-latex="inline" data-original-text="x">x</span>, the x-coordinates of the calculated point <span data-latex="inline" data-original-text="R">R</span> (as we will observe later)</li></ul><div>The public key is <span data-latex="inline" data-original-text="Q = d · G">Q = d \cdot G</span>, where <span data-latex="inline" data-original-text="G">G</span> is the curve’s generator point. During verification, a point <span data-latex="inline" data-original-text="R">R</span> is recomputed:</div> 
<span data-latex="block" data-original-text="">R = u_1 \cdot G + u_2 \cdot Q</span> 
<p>where:</p> 
<span data-latex="block" data-original-text="">\begin{gathered}r \cdot s^{-1} \equiv u_2 \pmod{n} \\ H(m) \cdot s^{-1} \equiv u_1 \pmod{n}\end{gathered}</span> 
<p>The signature is valid if:</p> 
<span data-latex="block" data-original-text="">x \equiv r \pmod{n}</span> 
<p><strong>2. Symmetry of ECDSA Signatures</strong></p><p>For any valid signature <span data-latex="inline" data-original-text="(r,s),">(r,s),</span> there exists another valid signature <span data-latex="inline" data-original-text="(r,s′)">(r,s')</span>, where <span data-latex="inline" data-original-text="s’ = n – s">s' = n - s</span>.<u><b><br/></b></u></p><p><u><b>Proof of validity:</b></u></p><ol><li>Replace <span data-latex="inline" data-original-text="s">s</span> with <span data-latex="inline" data-original-text="s′ = n – s">s' = n - s</span> in the verification equations:<ul><li>The inverse of <span data-latex="inline" data-original-text="s′">s'</span> modulo <span data-latex="inline" data-original-text="n">n</span> is: <span data-latex="inline" data-original-text="(s′)⁻¹ mod n = (n – s)⁻¹ mod n">(s')^{-1} \bmod n = (n - s)^{-1} \bmod n</span>.</li><li>Using modular arithmetic properties, this is equivalent to: <span data-latex="inline" data-original-text="(n – s)⁻¹ mod n = -s⁻¹ mod n">(n - s)^{-1} \bmod n = -s^{-1} \bmod n</span>.</li></ul></li><li>Compute <span data-latex="inline" data-original-text="u₁">u_1</span> and <span data-latex="inline" data-original-text="u₂">u_2</span> with <span data-latex="inline" data-original-text="s′">s'</span>:<ul><li><span data-latex="inline" data-original-text="u₁′ = H(m) · (s′)⁻¹ mod n = H(m) · (-s⁻¹) mod n = -u₁ mod n">u_1' = H(m) \cdot (s')^{-1} \bmod n = H(m) \cdot (-s^{-1}) \bmod n = -u_1 \bmod n</span>,</li><li><span data-latex="inline" data-original-text="u₂′ = r · (s′)⁻¹ mod n = r · (-s⁻¹) mod n = -u₂ mod n">u_2' = r \cdot (s')^{-1} \bmod n = r \cdot (-s^{-1}) \bmod n = -u_2 \bmod n</span>.</li></ul></li><li>Substituting these into the elliptic curve equation for <span data-latex="inline" data-original-text="R">R</span>:<ul><li><span data-latex="inline" data-original-text="R′ = u₁′ · G + u₂′ · Q = (-u₁) · G + (-u₂) · Q">R' = u_1' \cdot G + u_2' \cdot Q = (-u_1) \cdot G + (-u_2) \cdot Q</span>.</li><li>By group properties of elliptic curves: <span data-latex="inline" data-original-text="R′ = -(u₁ · G + u₂ · Q)">R' = -(u_1 \cdot G + u_2 \cdot Q)</span>.</li><li>The point <span data-latex="inline" data-original-text="R′">R'</span> is the negation of <span data-latex="inline" data-original-text="R">R</span>, but its x-coordinate remains the same:<span data-latex="inline" data-original-text=" R′ₓ = Rₓ">R'_x = R_x</span>.Thus, the verification condition <span data-latex="inline" data-original-text="Rₓ mod n = r">R_x \bmod n = r</span> is still satisfied.</li></ul></li></ol>

<p><strong>3. The Role of v in Solidity’s <span data-token-index="1">ecrecover</span><!-- notionvc: 23da689b-706f-4597-9f4b-0eda15f120ed --></strong></p><p>The <code data-token-index="1">ecrecover</code> function uses a recovery parameter <span data-latex="inline" data-original-text="v">v</span> to indicate which of two possible public keys to recover. The value of <span data-latex="inline" data-original-text="v">v</span> determines whether to use the original elliptic curve point <span data-latex="inline" data-original-text="R">R</span> or its negation <span data-latex="inline" data-original-text="-R">-R</span> during recovery:</p><ul><li><span data-latex="inline" data-original-text="v = 27">v = 27</span>: Corresponds to <span data-latex="inline" data-original-text="R">R</span></li><li><span data-latex="inline" data-original-text="v = 28">v = 28</span>: Corresponds to <span data-latex="inline" data-original-text="-R">-R</span></li></ul><div>If a valid signature <span data-latex="inline" data-original-text="(r, s, v)">(r, s, v)</span> is known with <span data-latex="inline" data-original-text="v = 27">v = 27</span> for example, one can construct another signature <span data-latex="inline" data-original-text="(r, s′ = n – s, v’)">(r, s' = n - s, v')</span> with <span data-latex="inline" data-original-text="v’ = 28">v' = 28</span>, as the verification condition remains valid for both cases.</div>
